## 시작하기 전에

루퍼스 10주를 지나면서 가장 크게 달라진 점은 AI를 쓰는 방식이다.

처음에는 AI에게 주제부터 던지고 시작했다.

"이거 어떻게 만들면 돼?"<br>
"배치 랭킹 만들어줘"<br>
"이 구조 괜찮아?"

이런 식으로 먼저 물어보고, AI가 제안한 답을 따라가려는 흐름이 많았다.

그런데 10주차에는 조금 달랐다.

이제는 설계부터 내가 직접 AI랑 정하고 시작했다.<br>
내가 원하는 설계를 AI는 모르기 때문이다.

AI가 코드를 잘 만들어줄 수는 있지만, 어떤 문제를 풀어야 하는지, 어떤 기준으로 구조를 나눌지, 어디까지 실시간으로 처리하고 어디부터 미리 계산할지는 결국 내가 정해야 했다.

이번 글은 10주 동안의 성장 회고로 시작하지만, 중심 내용은 10주차에 설계한 **주간/월간 상품 랭킹 배치 구조**다.

특히 MySQL에는 네이티브 구체화 뷰(Materialized View)가 없어서, 조회 전용 테이블을 만들고 배치로 삭제 후 재적재해서 구체화 뷰처럼 사용한 과정을 정리하려 한다.

## 10주차에서 풀어야 했던 문제

이전에는 일간 실시간 랭킹을 Redis ZSET으로 처리했다.

상품 조회, 좋아요, 주문 같은 이벤트가 발생하면 랭킹 점수를 Redis에 반영하고, 일간 랭킹 조회 API는 Redis에서 점수가 높은 상품을 읽는 구조였다.

일간 랭킹은 실시간성이 중요하다.

오늘 어떤 상품이 많이 조회되고 있는지,<br>
오늘 어떤 상품에 좋아요가 많이 눌리는지,<br>
오늘 어떤 상품이 많이 팔리는지를 바로 반영해야 하기 때문이다.

하지만 주간 랭킹과 월간 랭킹은 성격이 조금 다르다.

주간 랭킹은 특정 주의 여러 날짜 데이터를 합쳐야 하고,<br>
월간 랭킹은 특정 달의 여러 날짜 데이터를 합쳐야 한다.

이걸 랭킹 조회 요청이 들어올 때마다 계산하면 부담이 커진다.

요청이 들어올 때마다 기간 데이터를 읽고, 상품별로 합산하고, 점수를 계산하고, 정렬한 뒤 상위 100개를 뽑는다면 랭킹 조회 API 자체가 무거워진다.

그래서 주간/월간 랭킹은 요청 시점에 계산하지 않고, 배치가 미리 계산한 조회 모델을 읽도록 분리하기로 했다.

## 전체 구조

최종 구조는 아래처럼 나누었다.

![상품 랭킹 조회 아키텍처](/assets/images/posts/2026-07-20-ranking-architecture.svg)

_일간 랭킹은 Redis에서 바로 읽고, 주간/월간 랭킹은 배치가 만든 조회 전용 테이블에서 읽는다._

이 그림에서 핵심은 하나다.

**랭킹의 기간마다 조회 원천을 다르게 둔다.**

일간 랭킹은 이벤트가 발생할 때마다 점수가 바뀌어야 하므로 Redis를 사용했다. 반면 주간/월간 랭킹은 일간 지표를 모아 계산한 결과가 필요하므로 배치가 미리 만들어 둔 조회 전용 테이블을 사용했다.

이렇게 나누면 랭킹 조회 API는 복잡한 집계를 직접 하지 않아도 된다.

조회 요청이 들어오면 period 값만 보고 일간이면 Redis를 읽고, 주간이나 월간이면 조회 전용 테이블을 읽는다.

## 처음 생각한 설계: 구체화 뷰

처음 떠올린 설계는 구체화 뷰였다.

이미 product_metrics라는 일간 지표 테이블이 있었다. 이 테이블에는 날짜와 상품별로 조회 수, 좋아요 수, 판매 수, 판매 금액이 쌓인다.

이 데이터를 기준으로 주간/월간 랭킹을 만들면 흐름은 단순하다.

원본 데이터는 product_metrics에 두고, 랭킹 조회 API가 빠르게 읽을 수 있는 계산 결과를 따로 저장한다. 즉, 조회할 때마다 원본 데이터를 다시 집계하지 않고, 미리 계산된 결과를 읽는 방식이다.

이 구조를 설명하기에 가장 가까운 개념이 구체화 뷰였다.

뷰처럼 조회용 모델이지만,<br>
일반 뷰처럼 매번 원본 쿼리를 실행하는 것이 아니라,<br>
계산된 결과를 물리적으로 저장해두고 읽는 구조이기 때문이다.

## 그런데 MySQL에는 구체화 뷰가 없었다

문제는 MySQL이었다.

PostgreSQL에는 구체화 뷰를 만드는 네이티브 기능이 있지만, MySQL에는 같은 방식의 구체화 뷰가 없다. MySQL 8.4 공식 FAQ에서도 [구체화 뷰가 없다고 설명한다](https://dev.mysql.com/doc/refman/8.4/en/faqs-views.html).

그래서 실제 구현에서는 DB가 제공하는 구체화 뷰 기능을 사용하지 않았다.

대신 일반 테이블을 만들고, 그 테이블을 조회 전용 모델처럼 사용했다.

주간 랭킹 결과는 mv_product_rank_weekly에 저장하고,<br>
월간 랭킹 결과는 mv_product_rank_monthly에 저장한다.

테이블 이름에는 구체화 뷰를 뜻하는 mv를 붙였지만, 실제로는 MySQL의 뷰가 아니다.

배치가 미리 계산해서 채워 넣는 조회 전용 테이블이다. 이 글에서 말하는 구체화 뷰는 DB 네이티브 기능이 아니라, **구체화 뷰처럼 사용한 조회 모델**에 가깝다.

## 최종 설계: 조회 모델을 분리했다

최종 설계의 핵심은 조회 원천을 분리하는 것이었다.

- 일간 랭킹은 Redis ZSET을 조회한다.
- 주간 랭킹은 mv_product_rank_weekly를 조회한다.
- 월간 랭킹은 mv_product_rank_monthly를 조회한다.

일간 랭킹은 오늘의 이벤트를 빠르게 반영해야 한다.

그래서 상품 조회, 좋아요, 주문 같은 이벤트가 발생할 때 Redis 점수를 바로 갱신하고, 조회할 때도 Redis에서 현재 순위를 읽는다.

반면 주간/월간 랭킹은 실시간으로 매 순간 바뀌는 것보다, 특정 기간의 지표를 기준으로 정리된 결과가 중요하다.

그래서 product_metrics에 쌓인 일간 지표를 배치가 합산하고, 그 결과를 조회 전용 테이블에 저장한다.

이 구조에서 중요한 점은 주간/월간 랭킹을 조회 요청 흐름에서 계산하지 않는다는 것이다.

랭킹 조회 API는 조회만 하고,<br>
집계와 정렬은 배치가 담당한다.

## 배치가 맡은 일

배치 작업 이름은 productRankingAggregationJob으로 잡았다.

이 배치는 period와 baseDate를 받아서 어떤 기간을 집계할지 계산한다.

period가 weekly라면 기준일이 속한 주의 월요일부터 일요일까지를 집계한다.<br>
period가 monthly라면 기준일이 속한 달의 1일부터 말일까지를 집계한다.

기간을 정한 뒤 배치가 하는 일은 크게 세 단계다.

- 파라미터 검증: period와 baseDate가 올바른지 확인한다.
- 기존 결과 삭제: 같은 기간의 랭킹 결과가 이미 있으면 먼저 지운다.
- 랭킹 집계: product_metrics를 합산해 상위 100개 상품을 조회 전용 테이블에 다시 적재한다.

여기서 삭제 후 재적재 방식을 선택한 이유는 재실행을 단순하게 만들기 위해서다.

같은 기간의 결과가 남아 있는 상태에서 다시 적재하면 순위나 상품 기준의 중복이 생길 수 있다. 그래서 해당 기간 결과를 먼저 지우고, 다시 계산한 상위 100개를 넣는 방식으로 잡았다.

점수식은 조회 수, 좋아요 수, 판매 금액을 가중치로 합산하는 방식이다.

조회 수는 낮은 가중치로 반영하고,<br>
좋아요 수는 그보다 조금 높게 반영하고,<br>
판매 금액은 가장 높게 반영했다.

단순히 많이 본 상품보다 실제 구매로 이어진 상품을 더 강하게 반영하고 싶었기 때문이다.

## 조회 API는 어떻게 나눴나

랭킹 조회 API는 하나로 유지했다.

사용자는 같은 랭킹 API를 호출하되, period 값으로 일간, 주간, 월간 중 어떤 랭킹을 볼지 선택한다.

내부 흐름은 period 값에 따라 갈라진다.

- daily는 Redis에서 일간 실시간 랭킹을 읽는다.
- weekly는 기준일이 속한 주의 기간을 계산하고, 주간 조회 전용 테이블을 읽는다.
- monthly는 기준일이 속한 달의 기간을 계산하고, 월간 조회 전용 테이블을 읽는다.

겉으로는 하나의 API지만, 내부에서는 조회 원천이 다르다.

이렇게 나누면 API 사용 방식은 단순하게 유지하면서도, 각 랭킹의 성격에 맞는 저장소를 사용할 수 있다.

## 이 과정에서 성장한 점

예전이었다면 아마 이렇게 말했을 것이다.

"배치 랭킹 만들어줘."

하지만 이번에는 그렇게 시작하지 않았다.

먼저 어떤 랭킹을 실시간으로 처리할지 정했다.<br>
그다음 어떤 랭킹을 미리 계산할지 정했다.<br>
그리고 미리 계산한 결과를 어디에 저장하고, 조회 API가 어떤 기준으로 분기할지 정했다.

이번 구현에서 먼저 정한 것은 대략 이런 것들이었다.

- 일간 랭킹은 Redis를 조회한다.
- 주간/월간 랭킹은 조회 요청마다 계산하지 않는다.
- MySQL에는 네이티브 구체화 뷰가 없으므로 조회 전용 테이블을 구체화 뷰처럼 사용한다.
- 배치는 period와 baseDate를 받아 집계 기간을 계산한다.
- 같은 기간 결과는 삭제 후 다시 적재한다.
- 점수는 조회 수, 좋아요 수, 판매 금액에 가중치를 두고 계산한다.
- 조회 API는 period 값에 따라 Redis와 조회 전용 테이블로 분기한다.

이렇게 정리하고 나니 AI에게 요청하는 방식도 달라졌다.

"랭킹 만들어줘"가 아니라,<br>
"주간/월간 랭킹은 조회 전용 테이블을 만들고, 배치 작업 파라미터로 기간을 받아 삭제 후 재적재하는 구조로 구현하자"라고 말할 수 있었다.

요구가 구체적이니 AI가 만든 결과도 더 쉽게 검토할 수 있었다.

기간 계산이 맞는지,<br>
재실행할 때 기존 데이터가 삭제되는지,<br>
일간과 주간/월간의 조회 원천이 제대로 나뉘었는지 확인할 기준이 생겼기 때문이다.

AI를 쓰면서 느낀 점은, AI가 내가 모르는 정답을 대신 책임져주는 도구는 아니라는 것이다.

오히려 AI는 내가 이해하고 있는 문제와 설계를 더 빠르게 구현하게 해주는 도구에 가깝다.

내가 문제를 알고 있어야 AI에게 정확히 요청할 수 있고,<br>
내가 기준을 알고 있어야 AI가 만든 결과를 빠르게 검토할 수 있다.

검토가 빨라지면 한 가지 방식에 오래 묶이지 않고, 여러 설계를 더 많이 시도해볼 수 있다.

그래서 결국 공부를 해야 AI를 더 잘 쓸 수 있다고 느꼈다.

## 결론

10주 동안 달라진 점은 AI를 덜 쓰게 된 것이 아니다.

오히려 더 잘 쓰게 된 것에 가깝다.

처음에는 AI에게 주제부터 던졌지만, 이제는 내가 풀 문제와 설계를 먼저 정리한 뒤 AI와 구현한다.

이번 배치 랭킹 구현도 그 과정이었다.

MySQL에 네이티브 구체화 뷰가 없다는 제약을 확인했고,<br>
조회 전용 테이블을 구체화 뷰처럼 쓰는 방식으로 설계를 바꿨고,<br>
일간 랭킹과 주간/월간 랭킹의 조회 원천을 분리했다.

기술을 이해할수록 AI에게 더 정확히 요구할 수 있다.

AI는 공부를 대신해주는 도구라기보다, 내가 아는 지식과 설계를 더 빠르게 구현하게 해주는 도구였다.

결국 공부해야 AI의 결과를 검토할 수 있고, 검토할 수 있어야 더 나은 선택지를 고를 수 있다.
