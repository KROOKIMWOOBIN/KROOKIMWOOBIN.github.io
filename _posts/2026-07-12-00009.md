## 시작하기 전에

실시간 랭킹이라고 하면 조금 어렵게 느껴진다.

"사용자가 상품을 볼 때마다 순위를 바로 바꿔야 하나?"<br>
"좋아요가 눌릴 때마다 DB를 정렬해야 하나?"<br>
"주문까지 반영하려면 구조가 너무 복잡해지는 것 아닌가?"

처음에는 이렇게 생각할 수 있다.

하지만 핵심만 놓고 보면 실시간 랭킹은 그렇게 복잡한 문제가 아니다.

**랭킹에 영향을 주는 행동이 발생하면 점수를 올리고, 점수가 높은 순서대로 보여주는 구조**다.

예를 들어 상품 랭킹이라면 이런 행동들이 점수에 영향을 줄 수 있다.

- 상품 상세 조회
- 좋아요
- 좋아요 취소
- 주문 완료

이 글에서는 Kafka와 Redis ZSET을 사용해서 실시간 랭킹을 어떻게 구성할 수 있는지 정리해보려 한다.

## 실시간 랭킹은 무엇일까?

실시간 랭킹은 말 그대로 현재 시점의 순위를 사용자에게 보여주는 시스템이다.

예를 들어 쇼핑몰에서 "지금 인기 있는 상품"을 보여준다고 생각해보자.

어떤 상품은 조회가 많이 되고,<br>
어떤 상품은 좋아요가 많이 눌리고,<br>
어떤 상품은 실제 주문까지 많이 발생한다.

이런 행동들을 점수로 바꾸고, 점수가 높은 상품부터 보여주면 인기 상품 랭킹을 만들 수 있다.

단순하게 표현하면 아래와 같다.

```text
상품 조회 -> 점수 증가
좋아요 -> 점수 증가
주문 완료 -> 점수 증가
점수가 높은 상품 -> 랭킹 상위
```

여기서 중요한 점은 랭킹이 단순히 데이터를 보여주는 기능이 아니라는 것이다.

랭킹은 계속 바뀐다.

사용자가 상품을 볼 때마다,<br>
좋아요를 누를 때마다,<br>
주문이 완료될 때마다 랭킹 점수가 바뀔 수 있다.

그래서 실시간 랭킹을 만들 때는 "어디에 점수를 저장할 것인가"와 "어떻게 점수를 갱신할 것인가"를 먼저 생각해야 한다.

## DB에서 바로 정렬하면 안 될까?

가장 먼저 떠올릴 수 있는 방법은 RDB에 점수를 저장하고 정렬해서 조회하는 것이다.

예를 들어 상품 테이블에 `ranking_score` 같은 컬럼을 두고,<br>
조회나 좋아요가 발생할 때마다 값을 올린 뒤,<br>
랭킹 API에서는 점수가 높은 순서대로 정렬해서 가져올 수 있다.

흐름만 보면 단순하다.

```text
사용자 행동 발생
-> RDB의 상품 점수 증가
-> ORDER BY ranking_score DESC로 조회
```

하지만 이 방식은 트래픽이 많아질수록 부담이 커질 수 있다.

상품 조회는 매우 자주 발생하는 요청이다.<br>
좋아요도 짧은 시간에 많이 눌릴 수 있다.<br>
주문 완료 이벤트도 랭킹에 반영해야 할 수 있다.

이 모든 요청이 매번 RDB의 같은 점수 컬럼을 갱신한다면,<br>
사용자 요청 흐름이 랭킹 계산 때문에 무거워진다.

랭킹 조회도 마찬가지다.

점수 기준으로 계속 정렬해서 보여줘야 하는데,<br>
랭킹처럼 자주 조회되는 화면에서 매번 RDB 정렬에 기대는 것은 부담이 될 수 있다.

그래서 구조를 조금 나누어 생각하는 것이 좋다.

```text
사용자 요청을 처리하는 일
랭킹 점수를 계산하고 정렬하는 일
```

이 둘을 같은 흐름에서 모두 처리하지 않아도 된다.

## 구조를 나누면 쉬워진다

실시간 랭킹 구조는 크게 두 흐름으로 나눌 수 있다.

```text
1. 사용자 요청 흐름
2. 랭킹 계산 흐름
```

사용자 요청 흐름에서는 상품 조회, 좋아요, 주문 같은 실제 서비스 기능을 처리한다.

랭킹 계산 흐름에서는 그 행동들을 이벤트로 받아서 랭킹 점수를 갱신한다.

전체 구조를 단순하게 그리면 아래와 같다.

```text
사용자 행동
-> 서비스에서 요청 처리
-> Outbox에 이벤트 저장
-> Kafka로 이벤트 발행
-> 랭킹 Consumer가 이벤트 소비
-> Redis ZSET에 점수 반영
-> 랭킹 API에서 Redis ZSET 조회
```

이 구조의 핵심은 **사용자 요청 흐름과 랭킹 계산 흐름을 분리하는 것**이다.

사용자가 상품을 조회했다고 해서 그 요청 안에서 랭킹 계산까지 모두 끝낼 필요는 없다.<br>
상품 조회는 상품 조회대로 처리하고, "상품이 조회되었다"는 사실을 이벤트로 남긴다.

그 이벤트를 Kafka로 전달하면,<br>
랭킹을 담당하는 Consumer가 나중에 읽어서 Redis에 점수를 반영한다.

이렇게 하면 랭킹 계산이 사용자 요청 흐름을 직접 붙잡지 않는다.

## Kafka는 왜 필요할까?

Kafka는 여기서 이벤트를 전달하는 역할을 한다.

중요한 것은 Kafka를 "트래픽이 많을 때 쓰는 도구" 정도로만 이해하면 부족하다는 점이다.

이 구조에서 Kafka의 역할은 **관심사를 분리하는 것**에 가깝다.

사용자 요청을 처리하는 서비스는 본래의 일을 한다.

- 상품 조회 처리
- 좋아요 처리
- 주문 완료 처리

그리고 그 결과로 발생한 사실을 이벤트로 남긴다.

```text
PRODUCT_VIEWED
PRODUCT_LIKED
PRODUCT_UNLIKED
ORDER_PAID
```

랭킹 계산은 별도 Consumer가 맡는다.

즉, 사용자 요청 흐름은 서비스가 담당하고,<br>
랭킹 점수 계산은 다른 흐름에서 담당한다.

```text
서비스
-> 이벤트 발행
-> Kafka
-> 랭킹 Consumer
-> Redis ZSET 갱신
```

이렇게 나누면 랭킹 계산 로직이 서비스 핵심 로직 안에 섞이지 않는다.

또 Consumer가 잠깐 느려져도 Kafka에 이벤트가 쌓여 있다면 이후에 이어서 처리할 수 있다.<br>
그래서 Kafka는 단순한 비동기 도구라기보다, 이벤트 흐름을 분리하고 이어주는 장치로 볼 수 있다.

## Redis ZSET은 왜 랭킹에 잘 맞을까?

Redis ZSET은 Sorted Set이라고도 부른다.

이름 그대로 정렬된 집합이다.

ZSET에는 크게 두 값이 들어간다.

```text
member = 저장할 대상
score = 정렬 기준이 되는 점수
```

상품 랭킹에서는 이렇게 생각할 수 있다.

```text
member = productId
score = ranking score
```

예를 들어 아래처럼 저장된다.

```text
ranking:all:20260712

productId 1 -> 12.4
productId 2 -> 7.8
productId 3 -> 3.1
```

Redis는 ZSET 안의 데이터를 score 기준으로 정렬해둘 수 있다.

그래서 점수가 높은 상품부터 가져오거나,<br>
특정 상품이 몇 등인지 찾는 작업에 잘 맞는다.

랭킹 목록을 조회할 때는 높은 점수순으로 가져오면 된다.

```text
ZREVRANGE ranking:all:20260712 0 19 WITHSCORES
```

특정 상품의 현재 순위를 보고 싶다면 높은 점수 기준 순위를 조회하면 된다.

```text
ZREVRANK ranking:all:20260712 productId
```

Spring Data Redis에서는 이런 흐름이 `reverseRangeWithScores`, `reverseRank` 같은 메서드로 표현된다.

## 점수는 어떻게 올릴까?

랭킹 점수는 이벤트 종류에 따라 다르게 올릴 수 있다.

예를 들어 이런 기준을 둘 수 있다.

| 이벤트 | 점수 반영 |
|---|---:|
| 상품 조회 | +0.1 |
| 좋아요 | +0.2 |
| 좋아요 취소 | -0.2 |
| 주문 완료 | 주문 금액 기반 점수 |

상품 조회는 가벼운 관심 표현이다.<br>
좋아요는 조회보다 조금 더 강한 관심 표현이다.<br>
주문 완료는 실제 구매로 이어진 행동이기 때문에 더 큰 점수를 줄 수 있다.

현재 예시 구조에서는 주문 완료 이벤트를 받을 때 상품별 주문 금액에 가중치를 곱해 점수로 반영한다.

```text
상품 조회 -> productId에 +0.1
좋아요 -> productId에 +0.2
좋아요 취소 -> productId에 -0.2
주문 완료 -> 상품별 주문 금액 * 0.6
```

Redis ZSET에서는 점수를 누적할 때 `ZINCRBY`를 사용할 수 있다.

```text
ZINCRBY ranking:all:20260712 0.1 1
```

이 명령은 `ranking:all:20260712`라는 ZSET에서<br>
member가 `1`인 상품의 score를 `0.1`만큼 증가시킨다는 뜻이다.

좋아요 이벤트가 들어오면 같은 member에 다시 점수를 더한다.

```text
ZINCRBY ranking:all:20260712 0.2 1
```

그러면 상품 1번의 점수는 누적된다.

```text
0.1 + 0.2 = 0.3
```

핵심은 랭킹을 매번 새로 계산하는 것이 아니라,<br>
랭킹에 영향을 주는 이벤트가 들어올 때마다 Redis ZSET의 점수를 조금씩 갱신한다는 점이다.

## 날짜별 랭킹 키를 나눈다

랭킹은 보통 기간이 필요하다.

오늘의 인기 상품인지,<br>
이번 주 인기 상품인지,<br>
전체 누적 인기 상품인지에 따라 기준이 달라진다.

일간 랭킹이라면 날짜별로 Redis key를 나눌 수 있다.

```text
ranking:all:20260712
ranking:all:20260713
ranking:all:20260714
```

이렇게 하면 오늘 랭킹을 조회할 때는 오늘 날짜 key만 보면 된다.

```text
GET /api/v1/rankings?date=20260712&page=0&size=20
```

날짜별 key를 나누면 오래된 랭킹 데이터에 TTL을 걸기도 쉽다.

예를 들어 일간 랭킹을 이틀 정도만 유지한다면,<br>
Redis key에 2일 TTL을 걸어 오래된 랭킹을 자연스럽게 정리할 수 있다.

```text
ranking:all:20260712 -> 2일 뒤 만료
```

이렇게 하면 Redis에 랭킹 데이터가 끝없이 쌓이는 것도 막을 수 있다.

## 중복 이벤트는 조심해야 한다

Kafka를 사용하면 중복 처리를 반드시 생각해야 한다.

Consumer가 같은 이벤트를 두 번 처리할 수도 있다.

예를 들어 상품 조회 이벤트가 한 번 발생했는데,<br>
Consumer 재시도나 장애 복구 과정에서 같은 이벤트를 두 번 읽었다고 해보자.

그런데 매번 점수를 올리면 어떻게 될까?

```text
원래 점수: +0.1
중복 처리 후 점수: +0.2
```

실제로는 한 번 조회됐는데 랭킹 점수는 두 번 올라간다.

좋아요나 주문 완료 이벤트라면 문제는 더 커질 수 있다.<br>
주문 완료 이벤트가 중복 반영되면 특정 상품의 랭킹 점수가 과하게 올라간다.

그래서 랭킹 Consumer는 같은 이벤트를 한 번만 반영해야 한다.

이때 사용할 수 있는 기준이 `eventId`다.

```text
eventId = 이벤트를 구분하는 고유 값
```

랭킹을 반영하기 전에 이 eventId를 이미 처리했는지 확인한다.

```text
이미 처리한 eventId인가?
-> 맞다면 점수 반영 안 함
-> 아니라면 점수 반영 후 처리 완료 기록
```

## Outbox와 중복 방어는 역할이 다르다

여기서 Outbox와 중복 방어를 헷갈리면 안 된다.

Outbox는 이벤트를 Kafka로 안정적으로 발행하기 위한 패턴이다.

서비스 로직 안에서 어떤 일이 발생했을 때,<br>
그 이벤트를 바로 Kafka로만 보내면 문제가 생길 수 있다.

예를 들어 DB 저장은 성공했는데 Kafka 발행이 실패하면 어떻게 될까?

```text
상품 좋아요 처리 성공
-> Kafka 발행 실패
-> 랭킹 Consumer는 좋아요 이벤트를 모름
```

이렇게 되면 서비스 데이터와 랭킹 데이터 사이에 차이가 생긴다.

Outbox는 이런 문제를 줄이기 위해 이벤트를 먼저 DB에 저장한다.

```text
비즈니스 처리
-> 같은 흐름에서 Outbox 이벤트 저장
-> 별도 Relay가 Kafka로 발행
-> 성공하면 발행 완료 처리
-> 실패하면 나중에 재시도
```

즉 Outbox는 **이벤트 발행 누락을 줄이고, 실패한 발행을 재시도할 수 있게 하는 구조**다.

반면 중복 방어는 Consumer 쪽 문제다.

Kafka 이벤트가 Consumer에게 한 번 이상 전달될 수 있기 때문에,<br>
랭킹 점수를 같은 eventId로 여러 번 올리지 않도록 막아야 한다.

정리하면 아래와 같다.

| 구분 | 막으려는 문제 |
|---|---|
| Outbox | 이벤트가 Kafka로 발행되지 않고 사라지는 문제 |
| EventHandled | 이미 처리한 이벤트를 다시 처리하는 문제 |
| Redis SETNX | Redis 점수 반영을 같은 eventId로 중복 실행하는 문제 |

Outbox가 있다고 해서 Consumer 중복 처리가 자동으로 해결되는 것은 아니다.

이벤트를 안전하게 보내는 것과,<br>
받은 이벤트를 한 번만 반영하는 것은 서로 다른 문제다.

## Redis에서 한 번에 처리하는 이유

랭킹 점수를 올릴 때도 조심할 점이 있다.

단순히 아래처럼 나누어 처리하면 중간에 문제가 생길 수 있다.

```text
1. 처리한 eventId인지 확인한다
2. 처리하지 않았다면 점수를 올린다
3. 처리 완료로 기록한다
```

이 흐름이 여러 명령으로 나뉘어 있으면,<br>
중간에 장애가 나거나 동시에 같은 이벤트가 들어왔을 때 애매한 상황이 생길 수 있다.

그래서 Redis에서는 Lua script를 사용해 다음 작업을 하나의 흐름으로 묶을 수 있다.

```text
SETNX로 eventId 처리 여부 확인
-> 처음 보는 eventId이면 ZINCRBY로 점수 증가
-> ranking key와 handled key에 TTL 설정
```

이렇게 하면 Redis 안에서 중복 확인과 점수 증가가 함께 처리된다.

핵심은 이것이다.

```text
같은 eventId는 한 번만 점수를 올린다.
```

랭킹은 점수 누적이 중요한 기능이기 때문에,<br>
중복 이벤트를 막지 않으면 데이터가 쉽게 틀어진다.

## 랭킹 조회는 어떻게 할까?

랭킹 조회는 Redis ZSET에서 높은 점수순으로 가져오면 된다.

```text
ranking:all:20260712
-> score가 높은 productId부터 조회
```

API는 페이지와 사이즈를 받아서 필요한 구간만 가져올 수 있다.

```text
GET /api/v1/rankings?date=20260712&page=0&size=20
```

조회 흐름은 아래와 같다.

```text
랭킹 API 요청
-> Redis ZSET에서 productId와 score 조회
-> productId로 상품 정보 조회
-> 판매 중인 상품만 응답
-> rank, score, 상품 정보를 함께 반환
```

여기서 Redis에는 랭킹에 필요한 최소 정보만 둔다.

```text
productId
score
```

상품명, 브랜드, 가격 같은 상세 정보는 상품 저장소에서 조회해서 붙일 수 있다.

이렇게 하면 Redis는 랭킹 정렬에 집중하고,<br>
상품 정보는 기존 상품 도메인에서 관리할 수 있다.

## 완전한 실시간이라기보다 거의 실시간이다

Kafka와 Consumer를 사용하는 구조에서는 사용자의 행동이 발생한 즉시 랭킹에 반영된다고 단정하기는 어렵다.

이벤트가 Kafka에 쌓이고,<br>
Consumer가 그 이벤트를 읽고,<br>
Redis에 점수를 반영하는 시간이 필요하기 때문이다.

그래서 이 구조는 엄밀히 말하면 완전한 동기식 실시간이라기보다 **거의 실시간에 가까운 구조**다.

하지만 랭킹 같은 기능에서는 이 정도 지연이 허용되는 경우가 많다.

상품을 조회한 바로 그 순간 1밀리초 안에 랭킹이 바뀌어야 하는 경우는 드물다.<br>
대신 사용자 요청 흐름을 가볍게 유지하고,<br>
랭킹 계산을 별도 흐름으로 안정적으로 처리하는 것이 더 중요할 수 있다.

결국 중요한 것은 요구사항이다.

```text
반드시 즉시 반영되어야 하는가?
몇 초 정도 늦게 반영되어도 되는가?
중복 이벤트가 들어와도 점수가 정확해야 하는가?
랭킹 데이터는 며칠 동안 유지할 것인가?
```

이 질문에 답해야 구조를 제대로 설계할 수 있다.

## 전체 흐름 다시 보기

마지막으로 전체 흐름을 다시 정리해보자.

```text
1. 사용자가 상품을 조회하거나 좋아요를 누르거나 주문한다.
2. 서비스는 본래 요청을 처리한다.
3. 발생한 일을 Outbox 이벤트로 저장한다.
4. Relay가 Outbox 이벤트를 Kafka로 발행한다.
5. 랭킹 Consumer가 Kafka 이벤트를 읽는다.
6. 이벤트 타입에 따라 랭킹 점수를 계산한다.
7. Redis ZSET에 productId의 score를 증가시킨다.
8. 랭킹 API는 Redis ZSET에서 높은 점수순으로 조회한다.
```

이 구조에서 각 도구의 역할은 분명하다.

| 도구 | 역할 |
|---|---|
| Kafka | 사용자 요청 흐름과 랭킹 계산 흐름 분리 |
| Outbox | 이벤트 발행 누락 방지와 재시도 |
| Redis ZSET | productId별 랭킹 점수 저장과 정렬 |
| Consumer | 이벤트를 점수로 변환해 Redis에 반영 |

이렇게 보면 실시간 랭킹은 막연히 어려운 기능이 아니다.

결국 할 일은 세 가지다.

```text
어떤 행동을 점수로 볼지 정한다.
그 행동을 이벤트로 흘려보낸다.
Redis ZSET에 점수를 누적하고 높은 순서대로 조회한다.
```

## 결론

실시간 랭킹을 처음 보면 복잡해 보인다.

하지만 구조를 나누면 훨씬 단순해진다.

사용자 요청 흐름에서는 서비스의 본래 일을 처리하고,<br>
랭킹 계산 흐름에서는 Kafka 이벤트를 소비해 Redis ZSET의 점수를 갱신한다.

Redis ZSET에는 `productId`를 member로,<br>
랭킹 점수를 score로 저장한다.

조회, 좋아요, 주문 완료 같은 이벤트가 들어올 때마다 score를 증가시키고,<br>
랭킹 API는 score가 높은 순서대로 상품을 보여준다.

여기서 Outbox는 이벤트 발행 누락을 줄이기 위한 장치이고,<br>
EventHandled나 Redis SETNX 같은 중복 방어는 같은 이벤트가 랭킹 점수에 여러 번 반영되지 않도록 막는 장치다.

정리하면 실시간 랭킹의 핵심은 이것이다.

**랭킹을 매번 새로 계산하지 말고, 랭킹에 영향을 주는 이벤트를 점수로 바꿔 Redis ZSET에 누적한다.**

이 구조만 이해하면 Kafka와 Redis를 사용한 실시간 랭킹도 충분히 만들 수 있다.
