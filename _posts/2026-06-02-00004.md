## 시작하기 전에

락은 여러 작업이 동시에 같은 데이터에 접근할 때, 데이터 정합성이 깨지지 않도록 제어하는 방식이다.

예를 들어 재고가 1개 남았는데 100명이 동시에 구매 요청을 보내면,<br>
아무런 제어가 없을 경우 재고보다 많은 주문이 성공할 수 있다.<br>
이런 상황을 막기 위해 락을 사용한다.

락을 바라보는 방식은 크게 두 가지로 나눌 수 있다.

- **낙관적 락**: 충돌이 자주 발생하지 않는다고 보고, 실제 수정 시점에 데이터가 변경되었는지 검증한다.
- **비관적 락**: 충돌이 자주 발생할 수 있다고 보고, 데이터를 사용하는 동안 미리 잠가 다른 트랜잭션의 접근을 제한한다.

## 낙관적 락

낙관적 락은 충돌이 자주 발생하지 않는다고 가정하는 방식이다. 데이터를 조회할 때는 별도의 잠금을 걸지 않고,<br>
실제로 수정하는 시점에 내가 읽었던 데이터가 그 사이에 변경되었는지 검증한다.

> 낙관적 락은 이름에 `Lock`이 붙지만, 비관적 락처럼 DB row를 미리 잠그는 방식은 아니다.<br>
> 실제로는 `version` 컬럼을 조건으로 업데이트하면서, 내가 읽은 뒤 데이터가 변경되었는지 확인하는 **충돌 검증 방식**에 가깝다.<br>
> 물론 `UPDATE`가 실행되는 순간 DB 내부적으로 짧은 row lock은 발생할 수 있다. 하지만 이것은 데이터를 수정하기 위한 일반적인 DB 동작이고,<br>
> 비관적 락처럼 조회 시점부터 트랜잭션이 끝날 때까지 row를 점유하는 락과는 다르다.

보통 `version` 컬럼을 사용한다. 데이터를 수정할 때 내가 조회했던 `version`과 현재 DB의 `version`이 같으면 수정에 성공하고,<br>
다르면 다른 요청이 먼저 수정한 것으로 보고 실패 처리한다.

```sql
UPDATE product
SET stock = stock - 1,
    version = version + 1
WHERE id = 1
  AND version = 3;
```

위 쿼리에서 수정된 row가 0개라면, 이미 다른 트랜잭션이 먼저 데이터를 수정했다는 뜻이다.<br>
이때는 재시도할지, 사용자에게 실패 응답을 줄지 정책을 정해야 한다.

## 비관적 락

비관적 락은 충돌이 발생할 가능성이 높다고 가정하는 방식이다. 데이터를 조회하는 시점부터 DB row에 lock을 걸고,<br>
트랜잭션이 끝날 때까지 다른 트랜잭션이 해당 데이터를 수정하지 못하게 막는다.

대표적으로 `SELECT ... FOR UPDATE` 같은 방식이 있다.

```sql
SELECT *
FROM product
WHERE id = 1
FOR UPDATE;
```

비관적 락은 크게 공유 락(S-Lock)과 배타 락(X-Lock)으로 나눌 수 있다.

#### 공유 락(S-Lock)
공유 락은 읽기용 락이다. 여러 트랜잭션이 동시에 같은 row를 읽을 수 있지만, 다른 트랜잭션이 해당 row를 수정하는 것은 막을 수 있다.

#### 배타 락(X-Lock)
배타 락은 쓰기용 락이다. 하나의 트랜잭션만 획득할 수 있고, 같은 row에 대한 다른 수정 작업을 막는다.

공유 락을 직접 걸고 싶다면 일반 `SELECT`가 아니라 DB에서 제공하는 공유 락 문법을 사용해야 한다.

```sql
SELECT *
FROM product
WHERE id = 1
FOR SHARE;
```

공유 락은 내가 읽는 동안 다른 트랜잭션이 해당 row를 수정하면 안 되는 경우에 사용할 수 있다.<br>
예를 들어 특정 데이터를 기준으로 검증한 뒤, 같은 트랜잭션 안에서 그 검증 결과를 믿고 다음 로직을 처리해야 할 때 사용할 수 있다.

일반적으로 재고 차감, 계좌 이체처럼 데이터를 수정해야 하는 상황에서는 배타 락을 사용한다.<br>
대표적인 예시가 `SELECT ... FOR UPDATE`이다.

다만 DB에 따라 일반 조회까지 전부 막는 것은 아닐 수 있다.<br>
보통 문제가 되는 것은 같은 row에 대한 수정 요청이나, 또 다른 락 획득 요청이다.

비관적 락은 충돌을 미리 막을 수 있다는 장점이 있지만, 락을 오래 잡고 있으면 다른 요청들이 계속 기다리게 된다.<br>
그래서 트랜잭션 범위를 짧게 유지하고, `Lock Timeout`을 설정하는 것이 중요하다.

## 언제 어떻게 어떤 락을 사용해야 할까?

락을 선택할 때 가장 먼저 봐야 하는 기준은 **트래픽 양**이 아니라 **같은 데이터를 동시에 수정하는 요청이 얼마나 자주 발생하는지**다.

대량 트래픽 서비스라고 해서 무조건 비관적 락이 맞는 것은 아니다.<br>
트래픽이 많아도 각 사용자가 자기 데이터만 수정한다면 같은 row에 대한 동시 수정 경합은 낮을 수 있다.

반대로 요청 수가 많지 않아도, 여러 요청이 같은 재고 row나 같은 계좌 row를 동시에 수정한다면 경합은 높다.

기준별로 보면 아래처럼 나눌 수 있다.

- **같은 row 동시 수정 가능성**: 낙관적 락은 낮을 때, 비관적 락은 높을 때 적합하다.
- **DB row lock 선점 여부**: 낙관적 락은 미리 선점하지 않고, 비관적 락은 미리 선점한다.
- **실패 허용 여부**: 낙관적 락은 실패 후 재시도나 실패 응답이 가능해야 하고, 비관적 락은 가능하면 실패시키면 안 되는 경우에 사용한다.
- **처리량**: 낙관적 락은 평상시 처리량을 높게 가져가기 좋고, 비관적 락은 락 대기로 처리량이 낮아질 수 있다.
- **주요 위험**: 낙관적 락은 재시도 폭증과 Livelock, 비관적 락은 Deadlock과 Lock Timeout을 조심해야 한다.
- **대표 예시**: 낙관적 락은 여러 사용자가 수정할 수 있는 게시글이나 여러 기기에서 수정할 수 있는 프로필, 비관적 락은 재고 차감이나 계좌 이체에 자주 사용된다.

설계할 때는 아래처럼 판단하면 된다.

- **읽기 전용 API 또는 조회 화면**: 수정이 없으므로 충돌도 없다. 이 경우는 락이 필요하지 않다.
- **사용자가 자기 프로필을 단순 수정하는 경우**: 대부분 같은 row를 동시에 수정하지 않고, 마지막 저장이 이겨도 괜찮다면 보통 락 없이 처리할 수 있다.
- **같은 사용자가 여러 기기나 탭에서 동시에 수정할 수 있는 경우**: 이전 변경이 마지막 저장에 덮어씌워질 수 있으므로 낙관적 락을 고려한다.
- **관리자 여러 명이 같은 게시글이나 상품 정보를 수정하는 경우**: 수정은 드물지만 같은 row 충돌 가능성이 있으므로 낙관적 락을 고려한다.
- **같은 상품 재고를 여러 사용자가 동시에 차감하는 경우**: 같은 row를 동시에 수정하는 경합이 높으므로 비관적 락을 고려한다.
- **계좌 이체처럼 금액 정합성이 중요한 경우**: 실패시키기보다 순서대로 정확히 반영해야 하므로 비관적 락을 고려한다.

낙관적 락은 수정이 있다는 이유만으로 무조건 사용하는 것이 아니다.<br>
같은 데이터를 동시에 수정할 가능성은 낮지만, 충돌이 발생했을 때 이전 변경이 조용히 덮어씌워지면 안 되는 경우에 적합하다.<br>
예를 들어 여러 관리자가 같은 게시글을 수정하거나, 같은 사용자가 여러 기기에서 같은 정보를 동시에 수정할 수 있는 경우다.

비관적 락은 경합이 자주 발생하고, 늦게 들어온 요청이라도 순서를 기다려서 반드시 반영해야 하는 도메인에 적합하다.<br>
예를 들어 이벤트 재고 차감이나 계좌 이체처럼 정합성이 특히 중요한 경우다.

정리하면, **대량 트래픽인지가 아니라 같은 row를 동시에 수정하는지**를 먼저 봐야 한다.<br>
수정이 없으면 락은 필요하지 않다. 수정이 있어도 마지막 저장이 이겨도 괜찮다면 락 없이 처리할 수 있다.<br>
같은 row 수정 경합은 낮지만 변경 유실을 막아야 한다면 낙관적 락을 고려한다.<br>
같은 row 수정 경합이 높고 실패시키면 안 되며 순서대로 처리해야 한다면 비관적 락을 고려한다.

## 잘못된 락을 사용할 경우의 리스크

#### 낙관적 락의 리스크
낙관적 락은 충돌이 적을 때는 처리량이 좋지만, 충돌이 많은 상황에서는 오히려 실패와 재시도가 폭증할 수 있다.

예를 들어 100명 선착순 이벤트에서 모든 요청이 같은 재고 row를 수정하려고 하면,<br>
대부분의 요청이 version 충돌로 실패한다. 이때 모든 요청을 즉시 재시도시키면<br>
계속 충돌하면서 `Livelock`에 가까운 상황이 발생할 수 있다.

그래서 낙관적 락을 사용할 때는 아래 정책이 필요하다.

- 재시도 횟수를 제한한다.
- 재시도 간격을 둔다.
- 선착순 이벤트처럼 실패가 자연스러운 도메인은 즉시 실패 처리한다.
- 실패 응답을 사용자에게 어떻게 보여줄지 정한다.

#### 비관적 락의 리스크
비관적 락은 충돌을 미리 막을 수 있지만, 락을 잡는 순서가 꼬이면 `Deadlock`이 발생할 수 있다.

예를 들어 1번 상품 row와 2번 상품 row가 있을 때, 하나의 트랜잭션에서 여러 상품을 구매한다고 가정해보자.

- A 트랜잭션은 1번 상품을 먼저 잠그고, 이후 2번 상품을 잠그려고 한다.
- B 트랜잭션은 2번 상품을 먼저 잠그고, 이후 1번 상품을 잠그려고 한다.

이 경우 서로가 가진 락을 기다리게 되어 `Deadlock`이 발생할 수 있다.

그래서 비관적 락을 사용할 때는 아래 정책이 필요하다.

- 자원 접근 순서를 통일한다. 예를 들어 항상 ID 오름차순으로 lock을 획득한다.
- 트랜잭션 범위를 최대한 짧게 유지한다.
- `Lock Timeout`을 설정한다.
- 락을 잡은 상태에서 외부 API 호출처럼 오래 걸리는 작업을 하지 않는다.

## 결론
낙관적 락과 비관적 락 중 무엇이 무조건 더 좋다고 말하기는 어렵다. 중요한 것은 도메인에서<br>
같은 row를 동시에 수정하는 경합이 얼마나 자주 발생하는지, 실패를 허용할 수 있는지, 요청을 반드시 순서대로 처리해야 하는지다.

낙관적 락은 대량 트래픽 여부와 상관없이 같은 데이터에 대한 동시 수정 경합은 낮지만, 충돌 시 변경 유실을 막아야 할 때 적합하다.<br>
반대로 비관적 락은 같은 데이터를 동시에 수정할 가능성이 높고, 요청을 기다리게 해서라도 정합성을 지켜야 할 때 적합하다.

다만 비관적 락은 `Deadlock`, `Lock Timeout`, connection pool 고갈 같은 위험이 있으므로 트랜잭션 범위를<br>
짧게 유지하고 락 획득 순서를 통일해야 한다. 낙관적 락 역시 재시도 정책을 잘못 잡으면 오히려 장애로 이어질 수 있으므로,<br>
실패 처리 기준을 명확히 정해야 한다.
